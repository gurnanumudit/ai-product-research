# Financial answer review

For the article **Which financial AI answers should we review?**, start with the [article analysis supplement](article-analysis/README.md): scoring against FinQA’s answer key, review-budget comparisons, aggregate results, tests and reproduction limits. The [version 2 implementation](v2/README.md) is preserved separately.

## Historical Stage A

Stage A development code for a training-only feasibility study: can arithmetic and source checks help prioritize incorrect financial answers for review better than a model's stated confidence?

The Stage A files below contain implementation and tests, not an effectiveness claim. Actual reference adjudication, execution approvals and run artifacts stay local. Passing software tests does not establish that a review policy works. The later article supplement above documents the empirical results separately.

## Contents

- `prepare_data.py` acquires the pinned official FinQA training split, checks its hash and selects 50 questions deterministically. It writes answering inputs separately from evaluation references.
- `package/` contains the answer schema, prompt, bounded arithmetic/source checker, separate reference scorer and confidence/verification/random review policies.
- `runner.py` validates 50 requests offline by default. Its provider path requires a separately reviewed, one-use approval manifest binding code, inputs, annotations, runtime and exact requests; it never automatically retries.
- `summarize_pilot.py` preserves all planned questions and separates numerical matches, mismatches, unresolved references and operational failures. Unknown answers are not silently counted as errors or dropped.
- `tests/test_build.py`, `test_runner.py` and `test_summary.py` contain 72 offline tests using synthetic inputs only.
- `test_data.py` contains 10 additional local archive/audit tests. The required raw data and manual audit artifacts are not included in Git.

## Run the offline tests

From this directory, with Python 3.11 or newer:

```sh
python3 -m unittest discover -s tests -v
```

The 39 package tests require no third-party packages. For the additional 33 runner/report tests, install `requirements-runner.txt` in an isolated environment, then run `python3 -m unittest test_runner test_summary -v`. These tests make no provider calls and need no credentials or raw data; synthetic cost messages are test fixtures, not spending. They check numerical parsing, exact source locations, bounded arithmetic, gold isolation, explicit scoring conventions, common abstentions, matched review capacity and one-use execution guards. They also demonstrate limitations: correct arithmetic and a matching source number do not prove that the right financial metric or year was chosen.

## Optional data preparation

The source is [FinQA at commit 0f16e2867befa6840783e58be38c9efb9229d742](https://github.com/czyssrs/FinQA/tree/0f16e2867befa6840783e58be38c9efb9229d742). Acquisition requires `curl` and requests only its training file, README and license. The decoded training file is approximately 78 MB. No development/test file is acquired.

```sh
python3 prepare_data.py --out data
python3 -m unittest test_data -v
```

The destination must not already exist. Nine archive tests can run after acquisition; the tenth requires a separately created `data/reference-qualification.json` and is explicitly skipped if that manual audit is absent. The audit is not generated by downloading the dataset. Preserve the original references, the selected 50 IDs and the complete denominator; never replace examples based on model outcomes. The published code alone does not reproduce private manual adjudication or any model results.

## Offline request preflight

Install the optional dependencies in an isolated environment using `requirements-runner.txt`, then run:

```sh
python3 runner.py --inputs data/inputs.json --adjudication adjudication/annotations.json --out runs/new-preflight
```

The evaluator-only annotation file must be produced and reviewed separately; it is not bundled here or generated by the download command. The runner hashes it without sending its contents to the model. This command makes no provider call and writes an unapproved template. The transport candidate is the `openai/gpt-5.4-mini` gateway alias, with low reasoning, no tools, 4,096 maximum completion tokens, 50 attempts and no automatic retries. An alias is not a guaranteed immutable model snapshot. The runner has a USD5 Stage A ceiling and a prospective USD40 whole-study planning check, not authorization for a full study. The local `o200k_base` tokenizer cache must already exist; a cache miss fails instead of downloading it during preflight.

Do not use `--execute` until actual reference annotations, scoring precision, model identity, current prices, prompt/code hashes and the provider path have passed their execution review. A credential is not execution approval. This code does not create that approval automatically. Provider keys, raw responses and request traces must remain outside Git. `EXECUTION-CONSUMED.json` prevents automatic restart; never delete it to bypass a stopped or completed batch.

After an authorized run, create a new local report without rerunning the model:

```sh
python3 summarize_pilot.py --inputs data/inputs.json --adjudication adjudication/annotations.json --run runs/pilot-01 --out runs/pilot-01/new-summary.json
```

The annotation JSON contains a `records` list keyed by `id`, each with a `qualified` flag and a `scoring` mapping (or null). The qualified mapping follows the scorer fields below. The report checks saved request identity and input/annotation hashes against the run freeze. Unresolved-label accounting envelopes are not statistical confidence intervals or policy-effectiveness estimates.

## Scoring and review limits

The scorer requires an explicitly qualified reference with value, unit, scale, provenance, tolerance and tolerance provenance. It must not treat raw benchmark execution answers as independently verified truth or silently fix their scales to match a prediction. Ambiguous references remain unscorable, not model errors.

The policies see the same answers. At 20% review capacity, 50 questions give 10 review slots. Common mandatory abstentions consume those slots first; more than 10 makes the operating point infeasible. Flagged answers are withheld, not assumed corrected. The intended outcome is errors escaping review at equal workload, not a change in the model's underlying accuracy. This package contains no effectiveness estimates or human-productivity claims.
